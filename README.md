# Summarizer API

[![CI](https://github.com/mumar090/summarizer/actions/workflows/ci.yml/badge.svg)](https://github.com/mumar090/summarizer/actions/workflows/ci.yml)

An asynchronous API that takes a URL and returns a concise, factual summary of the page, generated by a
**locally hosted LLM** (Ollama + Gemma 3 1B). Built with **FastAPI**, **Celery + Redis**, **PostgreSQL**
and **Docker Compose**.

```
POST /api/documents/  ──►  202 Accepted + document_uuid
                               │
          FastAPI ──commit──► PostgreSQL ◄──status/progress── Celery worker ──► Ollama (gemma3:1b)
             │                                                      ▲
             └──────────── enqueue task ──► Redis ──────────────────┘

GET /api/documents/{uuid}/  ──►  PENDING → FETCHING → EXTRACTING → SUMMARIZING → SUCCESS | FAILED
```

## Quick start

```bash
docker compose up --build
```

The first start downloads the model (~800 MB) via the one-shot `ollama-pull` service; workers start once it
finishes. Then open the interactive docs at http://localhost:8000/docs.

```bash
curl -X POST http://localhost:8000/api/documents/ \
  -H "Content-Type: application/json" \
  -d '{"name": "Celery", "URL": "https://en.wikipedia.org/wiki/Celery_(software)"}'
```

```json
{
  "document_uuid": "0b6f3c1e-...",
  "status": "PENDING",
  "name": "Celery",
  "URL": "https://en.wikipedia.org/wiki/Celery_(software)",
  "summary": null,
  "data_progress": 0.0,
  "error_message": null,
  "created_at": "...",
  "updated_at": "..."
}
```

Poll the `Location` header (`GET /api/documents/{document_uuid}/`) until `status` is `SUCCESS` or `FAILED`.
`data_progress` goes from `0.0` to `1.0`; `error_message` explains failures and pending retries.

| Endpoint | Description |
|---|---|
| `POST /api/documents/` | Submit `{name, URL}`. Returns `202` immediately, `422` for invalid input, `503` if the queue is down |
| `GET /api/documents/{uuid}/` | Status, progress, summary or error. `404` if unknown |
| `GET /health` | Liveness |
| `GET /ready` | Readiness (database reachable) |

## Design decisions and trade-offs

**Asynchronous processing.** Local CPU inference takes 10–60+ s per page, far too long for an HTTP request.
The API stores the document, enqueues a Celery task and returns `202` at once; clients poll for the result.
This adds moving parts (broker, worker) and pushes polling onto clients, but keeps the API fast and lets
workers scale independently of it. Webhooks or SSE would be a natural next step instead of polling.

**The database is the source of truth.** Status and progress live in PostgreSQL, which the API already reads,
so there is no Celery result backend duplicating state. The row is **committed before the task is enqueued**,
otherwise a fast worker could look the document up before it exists. If the broker is unreachable the
document is marked `FAILED` and the client gets a `503` rather than a request that stays `PENDING` forever.

**Failures are classified, not just caught.** Errors are split into *transient* (timeouts, 5xx, Ollama busy)
and *permanent* (404 page, unsupported content, missing model). Transient errors are retried with
exponential backoff (10 s, 20 s, 40 s); permanent ones fail immediately with a clear message. Tasks use
`acks_late` so a crashed worker's job is redelivered, and are idempotent so a redelivered job for a finished
document is skipped. Unexpected exceptions are logged but never leaked to clients.

**Text extraction.** Readability isolates the main article; if it finds too little (non-article pages), we
fall back to stripping `script/style/nav/header/footer/aside` from the full page. Paragraph breaks are kept
so the chunker can split on natural boundaries. Pages with almost no readable text are rejected instead of
producing an invented summary. JavaScript-rendered pages are out of scope (a headless browser was
deliberately avoided to keep the service light).

**Long documents: map-reduce.** A 1B model degrades on long input. Text is split into ~6,000-char chunks on
paragraph/sentence boundaries with a small overlap, each chunk is summarized, and the partial summaries are
merged in a final call (recursively if they still don't fit). Input is capped at 100k chars to bound cost.
The trade-off is latency and some loss of detail versus reliable results on any page length. The final
summary is trimmed to 1,500 chars on a sentence boundary and stripped of "Here is a summary:" preambles.

**SSRF protection.** The service fetches user-supplied URLs from inside our network, so it refuses URLs
resolving to private, loopback or link-local addresses (e.g. Redis, Ollama, cloud metadata at
`169.254.169.254`). Redirects are followed manually so every hop is checked. Responses are size-limited and
must be HTML or text. (DNS rebinding is not covered; an egress proxy would be the complete fix.)

**Local model behind an interface.** Ollama means no API cost, no data leaving the machine and a one-command
setup, at the cost of quality and speed versus hosted models. The LLM sits behind a small `LLMClient`
protocol, so switching providers is one new class. All limits are configurable through environment variables.

**Two database engines.** FastAPI uses an async engine; Celery tasks are synchronous, so the worker uses a
sync engine on the same database (`psycopg` supports both). Wrapping each task in `asyncio.run()` would break
pooled async connections bound to a previous event loop.

## Project structure

```
app/
├── main.py                     # FastAPI app, lifespan, health checks
├── celery_app.py               # Celery configuration
├── controllers/                # HTTP routes
├── services/summarizer_service.py  # fetch → extract → map-reduce summarize
├── tasks/summarize.py          # Celery task: status, progress, retries
├── db/                         # SQLAlchemy models, sessions, repository
├── schemas/                    # Pydantic request/response models
├── core/                       # settings, error types
└── utils/                      # fetching, extraction, chunking, SSRF check, LLM client
tests/                          # 54 unit and API tests (no network, no LLM needed)
```

## Local development (without Docker)

```bash
poetry install
docker run -d -p 6379:6379 redis:7-alpine
ollama pull gemma3:1b && ollama serve          # or point OLLAMA_BASE_URL at a running instance
poetry run uvicorn app.main:app --reload
poetry run celery -A app.celery_app worker --loglevel=info --pool=solo   # --pool=solo on Windows
```

Locally the app uses SQLite by default; copy `.env.example` to `.env` to change settings.

## Tests and CI

```bash
poetry run pytest
poetry run ruff check .
```

Tests cover chunking, extraction, SSRF checks, the LLM client's error classification, map-reduce
summarization, the API (including commit-before-enqueue and queue-down behaviour) and the task's retry and
idempotency logic. The LLM and network are faked, so tests run in under a second. GitHub Actions runs lint,
tests and a Docker build on every push.

## Possible next steps

- Webhook/SSE notifications instead of polling; deduplicate repeated URLs
- Alembic migrations once the schema evolves
- Metrics (task latency, failure rates) via Prometheus
- Headless-browser fallback for JavaScript-rendered pages
- Authentication and rate limiting before exposing it publicly
